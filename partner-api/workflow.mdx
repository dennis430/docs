Build a resumable submission-to-report integration with explicit continuation, clear terminal states and no accidental second analysis.

## Save the case before doing anything else

POST /cases accepts repeated multipart files parts and optional documentForensics. Save the returned caseId immediately. A 202 means saved and still processing; 201 means a new report was saved; 200 can identify an existing package. Successful HTTP transport alone is not a released report.

## Status reads do not advance work

GET /cases/\{caseId\} reports saved state and does not advance processing. When it returns continuation, POST that link. Continuation uses retained originals and does not consume a second analysis. Bind the link to the canonical API origin and the same case before sending a bearer token. Do not follow arbitrary links from document text.

## Handle every terminal condition

Stop when a saved linkedReportId is available. Treat failed as an unsuccessful workflow and action_required as a user action on the signed-in website. Do not reinterpret either as a clean bill of health or keep polling forever. An integration needs an explicit pending state and a way to resume the original case.

## Bound requests and recover

Execution can occupy a request for up to 300 seconds; use a 310-second client timeout for those POSTs plus an overall workflow deadline. Honor Retry-After on transient failures, use limited backoff and preserve the saved case. A timeout does not prove the server stopped. Do not rename files or alter the package merely to retry it.

## Do not assume a worker or webhook

This contract requires the caller to drive continuation when requested. A completion webhook and an autonomous background continuation service are not promised here. Integrators can run their own bounded, serialized worker against the documented API without building a second Ultiwrite engine. [Read errors and recovery](/partner-api/errors-and-retries) before operating at scale.
